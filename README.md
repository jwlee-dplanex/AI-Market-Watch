# AI Market Watch

국내 금융권의 AI 도입 동향을 수집하고 분석하여 주간 보고서로 축적하는 리서치 플랫폼입니다.

은행과 보험사가 AI를 어디에 도입하고 어떤 AI 기업과 무엇을 진행하는지를 뉴스에서 수집합니다. 수집한 기사에서 관련 없는 것을 걸러내고, 같은 사건을 하나의 이슈로 묶고, 그 이슈가 사업에 갖는 의미를 시사점으로 정리합니다. 정리된 내용은 주간 보고서가 되고 기업 사이의 관계는 지식그래프로 남습니다.

일회성 조사와 다른 점은 결과가 누적된다는 것입니다. 기사와 이슈와 시사점과 보고서가 서로 연결된 채 쌓이므로, 특정 기업이나 기술 주제가 어떤 경로를 거쳐 지금에 이르렀는지를 나중에 되짚을 수 있습니다.

⚠️ **AI 기업 단독 동향은 범위 밖입니다.** 금융사나 보험사가 관여한 건만 다룹니다.

## 제품의 성격

**수집은 코드가 수행하고 판단은 AI 에이전트가 수행합니다.**

기존 조사에서 시간이 소요되던 단계는 검색이 아니라 그 이후였습니다. 기사를 읽고 관련 여부를 가리며, 동일 사건을 하나로 묶고, 무엇이 중요한지 결정하는 단계입니다. 이 판단을 research-analyst 에이전트가 사람과 같은 방식으로 수행합니다. 기사 본문을 직접 읽고, 문서로 고정된 기준에 대조하며, 근거를 남깁니다.

- **판단 기준이 문서로 고정되어 있습니다.** 무엇을 노이즈로 볼지, 무엇을 하나의 이슈로 묶을지, 어떤 이슈가 더 중요한지가 `docs/planning.md`에 조항으로 기재되어 있습니다. 담당자가 바뀌어도 기준은 유지됩니다.
- **모든 서술에 근거가 따라붙습니다.** 모든 문장은 실제 수집 기사로 소급 가능해야 하며, 날조 금지가 최우선 원칙입니다.
- **제외한 기사도 보존됩니다.** 관련 없다고 판정하여 삭제한 기사도 본문과 태그와 판정 사유가 남습니다. 이 기록이 판정을 자동화할 때의 정답지가 됩니다.

⚠️ **판정을 거치지 않은 수집물은 사용할 수 없습니다.** 수집 대비 노이즈 비율이 실측에서 94%와 95%였습니다. 키워드 오탐, 동일 사건 중복 보도, 금융과 무관한 AI 일반 기사가 대부분입니다. 수집 자동화만으로는 활용 가능한 정보가 되지 않으며, 검증 게이트와 에이전트 판정이 그 간격을 메웁니다.

| 메뉴 | 내용 | 화면 ID |
|---|---|---|
| 대시보드 | 헤드라인 최대 3건과 주요 이슈 목록과 핵심 지표 | `ALL-001` |

| 지식그래프 | 금융사와 AI 기업 사이의 실제 관계망. 에이전트가 라벨링한 관계만 엣지로 표시합니다 | `GRAPH-001` |
| 뉴스 | 수집과 검증을 마친 기사 목록과 상세 | `NEWS-001~002` |
| 교보 소식 | 교보그룹 관계사 뉴스. 본 파이프라인과 데이터가 분리되어 있습니다 | `ROOM-001~003` |
| 설정 | 데이터소스, 수집 키워드, 프롬프트, Slack, 처리 이력, 기업, 기술 주제, 뉴스룸, 실행 | `SET-001~010` |

🔴 **수집과 에이전트 작업은 사람이 설정 > 실행(`SET-010`)에서 버튼을 눌러야 시작됩니다.** 스케줄 자동 실행은 2026-09-04에 폐기되었습니다. 서버가 예정 시각에 기동되어 있지 않으면 그날 실행이 예약조차 되지 않는 구조였고, 실제로 5회 연속 미실행이 발생했습니다.

⚠️ **수집된 기사는 즉시 화면에 노출되지 않습니다.** 에이전트가 관련성 판정을 마치고 검증 완료로 전환한 기사만 표시됩니다. 따라서 수집 직후에는 화면이 변하지 않고, 판정이 끝난 시점에 검증된 기사가 함께 반영됩니다.

## 빠른 시작

사전 준비는 Python 3.12와 Docker와 `.env` 파일입니다. `.env`는 `.env.example`을 참고하여 작성합니다.

```bash
python -m venv venv
venv\Scripts\pip install -r requirements.txt
copy .env.example .env
docker compose up -d db
venv\Scripts\python manage.py migrate --settings=config.settings.local
venv\Scripts\python manage.py runserver --settings=config.settings.local
```

`http://127.0.0.1:8000/`에서 확인합니다. 모든 `manage.py` 명령에는 `--settings=config.settings.local`을 붙여야 합니다. 기본값은 존재하지 않는 경로입니다.

🔴 **`requirements.txt`는 전이 의존성까지 전부 `==`로 고정되어 있습니다.** 로컬과 프로덕션을 동일하게 유지하기 위한 것이므로, 패키지를 새로 설치하거나 갱신한 뒤에는 `pip freeze`로 이 파일을 다시 생성해야 합니다.

## 프로덕션

AWS 클라우드 환경(EC2)에서 운영됩니다.

```
Django 5.2  ←  gunicorn (systemd 관리)  ←  WhiteNoise (정적 파일)
                      │
              PostgreSQL 16 + pgvector (Docker)
```

Django 애플리케이션을 gunicorn이 구동하고 프로세스는 systemd가 관리합니다. 데이터베이스는 Docker 컨테이너로 실행하며, 정적 파일은 WhiteNoise가 직접 서빙합니다. 별도의 웹 서버나 로드밸런서는 두지 않은 최소 구성입니다.

로컬 개발 환경과 프로덕션은 같은 구조를 유지합니다. 차이는 `runserver` 대신 gunicorn을 사용한다는 점뿐이며, Python 버전과 패키지 버전까지 동일하게 고정되어 있습니다. 개발은 `develop`에서 하고 배포는 `main`에서 합니다. 🔴 **병합하지 않으면 배포해도 반영되지 않습니다.** 배포 절차와 운영 규칙은 [`docs/dev.md`](./docs/dev.md) 10장에 있습니다.

## 개발 방식

`.claude/agents/`에 정의된 4개 서브에이전트로 개발하고 운영합니다. 호출은 사용자가 명시적으로 요청할 때만 이루어지며 자동으로 위임되지 않습니다.

PM과 PD와 PE는 플랫폼을 만드는 축이고 RA는 플랫폼을 사용하는 축입니다. 앞의 셋이 개발을 대신한다면 **RA는 운영 업무 자체를 대신합니다.** 작업 유형별 호출 순서를 포함한 전체 규칙은 [`CLAUDE.md`](./CLAUDE.md)에 있습니다.
