# AI Market Watch

DPLANEX 전략기획팀을 위한 내부 리서치 자산 플랫폼입니다. 국내 금융권(은행·보험사)의 AI/AX 도입 동향과 그와 연결된 AI 기업 동향(금융사·보험사가 관여한 협업·도입·검토)을 수집·정리해서, 일회성 리서치가 아니라 누적되는 정보 자산을 만드는 것이 목적입니다. (AI 기업 단독 동향은 스코프 밖입니다.)

## 이 제품의 성격 — 사람이 하던 판단을 AI가 한다

**모으는 것은 코드가 하고, 판단하는 것은 AI 에이전트가 합니다.**

기존 리서치에서 시간을 잡아먹던 일은 검색이 아니라 그 뒤였습니다 — 기사를 읽고 관련 있는지 가리고, 같은 사건끼리 묶고, 그래서 무엇이 중요한지 쓰는 일이요. 그 판단을 **AI 에이전트(research-analyst)가 사람과 같은 방식으로** 합니다. 기사 본문을 직접 읽고, 문서로 정해둔 기준에 대어 보고, 근거를 남깁니다.

그래서 이 제품에는 **"AI가 자동으로 요약해 주는" 상시 파이프라인이 없습니다.** 대신 이런 것들이 있습니다.

- **판단 기준이 문서로 고정돼 있습니다** — 무엇을 노이즈로 볼지, 무엇을 하나의 이슈로 묶을지, 어떤 이슈가 더 중요한지가 전부 `docs/planning.md`에 조항으로 적혀 있고, 에이전트는 그걸 읽고 따릅니다. 사람이 바뀌어도 기준은 안 바뀝니다.
- **판단에는 근거가 따라붙습니다** — 모든 문장은 실제 수집 기사로 거슬러 올라갈 수 있어야 하고, 지어내지 않는 것이 최우선 원칙입니다.
- **버린 것도 남습니다** — 관련 없다고 판정해 지운 기사도 본문·태그·판정 사유가 그대로 보존됩니다. 이 기록이 나중에 판정을 자동화할 때의 정답지가 됩니다.

한 줄로 줄이면 — **검색·정리를 자동화한 게 아니라, 읽고 판단하는 일을 옮긴 것입니다.**

## 문제 정의

AI 시장은 빠르게 바뀌고, 전략기획팀은 그 변화를 사업 방향과 연결해 해석해야 합니다. 그런데 기존 방식은 담당자가 직접 검색하고 문서로 정리하는 수작업이라 다섯 가지 한계가 있었습니다.

1. **시간이 많이 든다** — 담당자가 직접 검색하고 정리해야 합니다.
2. **흐름이 안 보인다** — 기사와 자료가 개별로 관리되어 유사 이슈나 시장 흐름을 파악하기 어렵습니다.
3. **기준이 사람마다 다르다** — 조사자마다 분류 기준과 해석 관점이 달라 일관된 인사이트가 안 나옵니다.
4. **사업 기회와 안 이어진다** — 수집된 뉴스가 실제 사업 기회와 어떻게 연결되는지 파악하기 어렵습니다.
5. **보고서가 수작업이다** — 정기적으로 공유할 보고서를 만드는 과정이 사람 손에 의존합니다.

AI Market Watch는 이 반복 업무를 자동화하고, **단순 뉴스 요약을 넘어 시사점과 사업 기회를 도출**하기 위해 만들었습니다.

## 핵심 가치

1. **금융권 AI/AX 동향 수집 자동화** — 국내 금융권(은행·보험사)의 AI/AX 도입 동향과, 그와 연결된 AI 기업 동향을 모읍니다.
2. **요약·관련성 판단** — 수집된 정보를 요약하고, 프로젝트 관심사에 실질적으로 관련 있는 기사인지 판단합니다.
3. **유사 기사 묶기** — 개별 기사가 아니라 **이슈 단위**로 묶어 반복되는 주제와 시장 흐름을 봅니다.
4. **시장 시사점 도출** — 요약을 넘어 그 동향이 사업에 갖는 의미와 활용 가능성을 정리합니다.
5. **주간 보고서 정기 작성** — 표준 구조에 따라 전략기획팀이 공유할 수 있는 형태로 만듭니다.
6. **정보 자산 축적** — 일회성 리서치가 아니라 기사·요약·이슈·시사점·보고서가 **누적**됩니다.

각 항목의 상세 정의와 판단 기준은 [`docs/planning.md`](./docs/planning.md)에 있습니다.

## 무엇을 하는 서비스인가

- **수집** — Naver News API 등에서 AI/AX 관련 키워드로 뉴스를 모읍니다. **실행 방식은 환경에 따라 다릅니다** — 로컬은 설정 > 데이터소스(SET-001)의 "지금 수집"으로 사람이 직접 돌리고, 프로덕션은 평일 오전 9시 스케줄로 자동 실행합니다. 스케줄러가 `runserver` 프로세스 안에 있어서 서버가 9시에 떠 있지 않으면 그날 실행이 예약조차 되지 않기 때문입니다(자세한 내용은 [`docs/dev.md`](./docs/dev.md) 8장). **로컬에서 아침에 수집이 안 돼 있어도 버그가 아닙니다.**
- **에이전트가 정제·집필** — 수집은 자동이지만, 노이즈 판정·삭제·이슈 그룹핑·시사점 작성·주간 보고서 편집은 research-analyst(RA) 에이전트가 사용자 호출에 따라 온디맨드 세션에서 직접 수행합니다(상시 자동 분류·요약 파이프라인 없음 — 모든 콘텐츠는 실제 수집 기사에 근거해야 하며 날조 금지가 최우선 원칙입니다).
- **검증 전에는 노출하지 않음** — 수집된 뉴스는 곧바로 화면에 나타나지 않습니다. RA가 관련성 판정을 마치고 검증 완료로 전환한 뉴스만 대시보드·목록·지식그래프에 노출됩니다. 수집량의 상당수가 키워드 오탐이나 동일 사건 중복 보도라(실측 사례: 57건 중 54건), 판정 전 뉴스를 그대로 보여주면 "이 서비스가 선별한 뉴스"로 오해되기 때문입니다. 그래서 **수집 직후에는 화면이 변하지 않고, RA 처리가 끝난 시점에 검증된 뉴스가 한꺼번에 올라옵니다.** 미처리 배치가 쌓이고 있는지는 설정 > 로그(SET-006)에서 운영자가 확인합니다.
- **대시보드로 한눈에** — 기간별(전체/최근 30일/최근 7일) 뉴스 추이, 기업별·기술주제별 언급 순위, 주요 이슈(Insight), 기업 간 관계망(지식그래프)을 대시보드에서 확인합니다.

## 기대 효과

위 문제 정의의 다섯 가지 한계에 하나씩 대응합니다. 괄호 안 수치는 **2026-08-07 실측값**이며, 운영이 쌓이면 달라집니다.

| 기존 한계 | 이 서비스가 바꾸는 것 |
|---|---|
| **① 시간이 많이 든다** | 검색·수집 단계가 사라집니다. 담당자는 **판정과 해석부터** 시작합니다 (수집 키워드 20개, 배치당 50건 안팎 유입) |
| **② 흐름이 안 보인다** | 기사가 **이슈 단위(Insight)로 묶이고**, 기업 간 관계는 지식그래프에 남습니다 (검증 뉴스 107건 → Insight 63건, 라벨 관계 14건) |
| **③ 기준이 사람마다 다르다** | 관련성 판단 기준·승격 위계가 **문서로 고정**되고, 판정 결과가 근거와 함께 쌓입니다 (삭제 판정 193건, 태그 교정 49건) |
| **④ 사업 기회와 안 이어진다** | 공급계약·기술협업·투자처럼 **사업 기회에 직결되는 접점을 1급으로 따로** 구분합니다 (1급 24 / 2급 32 / 3급 7) |
| **⑤ 보고서가 수작업이다** | 표준 구조와 출처 규약이 정해져 있어, 매주 **같은 형태로** 만들어집니다 |

**⑥ 그리고 버린 것도 남습니다.** 관련 없다고 판정해 지운 기사도 본문·태그·판정 사유가 그대로 보존됩니다. 이 기록이 **판정 자동화를 만들 때의 정답지**가 됩니다.

> ⚠️ **판정 없이는 못 씁니다.** 수집 대비 노이즈 비율이 8월 6일 48건 중 **43건(90%)**, 8월 7일 57건 중 **54건(95%)**이었습니다. 키워드 오탐, 동일 사건 중복, 금융과 무관한 AI 일반 기사 등입니다. 수집 자동화만으로는 쓸 수 있는 정보가 되지 않고, **검증 게이트와 RA 판정이 그 사이를 메웁니다.**

## 기술 스택

- **Backend**: Django 5.2 (서버 사이드 렌더링, 별도 API 레이어 없음)
- **Frontend**: HTMX(부분 업데이트) + Alpine.js(클라이언트 UI 상태) + Tailwind CSS
- **DB**: PostgreSQL 16 + pgvector (Docker)
- **외부 연동**: Naver News API, OpenDART API, Claude API(Anthropic), Voyage AI(임베딩), Slack Webhook
- **스케줄링**: APScheduler (in-process, `runserver`와 함께 기동 — 그래서 서버가 꺼져 있으면 그 시각 작업이 실행되지 않습니다. 로컬은 스케줄 비활성, 수동 수집)
- **시각화**: D3.js(지식그래프), 순수 SVG(대시보드 차트)

## 시작하기

### 사전 준비
- Python 3.12
- Docker (PostgreSQL 16 + pgvector 실행용)
- `.env` 파일 (`.env.example` 참고 — Naver/OpenDART/Anthropic/Voyage/Slack API 키 필요)

### 설치 및 실행

```bash
# 1. 가상환경 생성 및 패키지 설치
python -m venv venv
venv\Scripts\pip install -r requirements.txt   # Windows
# venv/bin/pip install -r requirements.txt      # macOS/Linux

# 2. .env 파일 생성
copy .env.example .env   # Windows
# cp .env.example .env    # macOS/Linux
# 이후 .env를 열어 실제 API 키·DB 정보를 채워 넣습니다.

# 3. DB 컨테이너 시작
docker compose up -d

# 4. 마이그레이션
venv\Scripts\python manage.py migrate --settings=config.settings.local

# 5. 개발 서버 실행
venv\Scripts\python manage.py runserver --settings=config.settings.local
```

`http://127.0.0.1:8000/`에서 확인할 수 있습니다.

모든 `manage.py` 명령에는 `--settings=config.settings.local`을 붙여야 합니다(기본값은 존재하지 않는 경로입니다).

## Claude Code 서브에이전트 (PM/PD/PE/RA)

이 프로젝트는 `.claude/agents/`에 정의된 4개의 전담 서브에이전트로 개발·운영됩니다. 호출은 사용자가 "PM/PD/PE/RA 불러줘"처럼 명시적으로 요청할 때만 이뤄지며, 자동으로 위임되지 않습니다.

**앞의 셋(PM·PD·PE)은 플랫폼을 만드는 축, RA는 플랫폼을 쓰는 축**입니다. *"사람이 하던 판단을 AI가 한다"*가 가장 직접적으로 드러나는 것은 **RA**입니다 — 나머지 셋은 개발을 대신하지만, **RA는 운영 업무 자체를 대신**합니다.

| 에이전트 | 역할 | 직접 수정 가능 범위 |
|---|---|---|
| **product-manager (PM)** | **기능 우선순위와 제품 정책 정의** — 무엇을 관련 있다고 볼지, 어떤 이슈가 더 중요한지의 기준을 문서로 고정 | `docs/planning.md` |
| **product-designer (PD)** | **화면 설계와 디자인 시스템** — 무엇을 어떤 순서로 보여줄지 결정 | `docs/design.md`, `templates/` |
| **product-engineer (PE)** | **실제 구현** — 데이터 모델·화면·수집 파이프라인 개발 | 제한 없음 |
| **research-analyst (RA)** | **수집된 뉴스로 산출물 생성** — 노이즈 판정·삭제, 같은 사건 묶기, 중요도 등급 부여, 시사점 작성, 주간 보고서 집필, 지식그래프 관계 라벨링 | 제한 없음(단 `.py` 구현은 소프트 제약) |

작업 유형별 호출 순서(신규 화면: PM→PD→PE, 버그 수정: PE만 등)를 포함한 전체 규칙은 [`CLAUDE.md`](./CLAUDE.md#서브에이전트-pmpdpera)를 참고하세요.
